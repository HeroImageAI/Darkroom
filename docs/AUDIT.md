## 2. Request flow

```
Browser (React)                     Darkroom server (Fastify)                      ComfyUI 0.37.4
───────────────                     ─────────────────────────                      ──────────────
screen builds {workflow, params,  → POST /api/jobs ─→ JobManager.submit
 meta}  (prompt text composed         buildPrompt(template, manifest spec, params)
 in the UI — see PROMPT_AUDIT)        family change or video? → POST /free  ─────→ unload between prompts
                                      video? → VRAM check (409 warning)
                                      POST /prompt (+extra_pnginfo, preview) ─────→ queue
UI ← WS /api/events ←──────────────  relays status/progress/preview  ←──────────── WS /ws (server's own clientId)
                                      on success: /history → /view → sharp thumb
                                      → items row (+lineage) → broadcast 'library'
```

- Inputs go to ComfyUI via `/upload/image` (subfolder `darkroom`); library items are re-uploaded on demand (`as-input`).
- Outputs are never read from disk paths; always through `/view` (Range-proxied for video).
- Jobs survive page reloads (server owns them) and server restarts (`resync()` reconciles with `/queue` + `/history`).
- Extend +5 s is a server-side chain (continuation job → `video_join`).

## 3. Model loading and VRAM policy (today)

| Family key | Models | Resident size (approx.) | Workflows |
|---|---|---|---|
| `klein` | flux-2-klein-9b-fp8mixed (9.0 GB) + qwen_3_8b_fp8mixed (8.3 GB) + flux2-vae | ~17 GB | klein_t2i, klein_ref, klein_edit, inpaint, outpaint |
| `qwen` | qwen_image_2.1_int8_convrot (7.3 GB) + qwen3vl_8b_int8_convrot (9.35 GB) + 2.1 VAE | ~17 GB | qwen_t2i, qwen_ref, qwen_edit, qwen_inpaint, qwen_outpaint |
| `seedvr2` | seedvr2_7b_sharp_int8 (7.9 GB) + ema VAE | ~8.5 GB | upscale |
| `wan` | Wan 2.2 I2V high + low fp8 (2×14.3 GB, streamed) + umt5 fp8 + lightx2v LoRAs | peaks 22–23 GB | wan22_i2v |
| `ltx` | LTX-2.5 22B distilled int8 (21.5 GB) + Gemma-4 12B int8 (15.4 GB) | peaks 24–25 GB | ltx25_i2v |
| `util` | BiRefNet, RIFE, trivial nodes | small | remove_bg, video_interp, video_join, crop, import, video_frame |

Policy in `JobManager.submit`: `POST /free {unload_models, free_memory}` whenever the family changes (ignoring `util`) and
before every video job; ComfyUI applies it between prompts, so a running job is never interrupted. Video jobs additionally
check free VRAM against `manifest.vramNeedGB`. ComfyUI's DynamicVRAM streams weights that don't fit.

Gaps found: (a) `family` of `qwen_edit`/`qwen_inpaint`/`qwen_outpaint` is `qwen` — correct; but `upscale` is family
`seedvr2` and `remove_bg` is `util`, so an Upscale directly after Qwen triggers a free (good) while Remove BG does not
(fine, it is small). (b) No family for a future VLM — needs one (`vlm`) so captioning evicts diffusion models and vice
versa. (c) `/free` is fire-and-forget; no measurement that memory actually dropped before a large job (only video checks).

## 8. Known issues found during this audit (not yet fixed)

1. **Qwen outpaint from the UI sends the raw user text.** The "extend the scene" wording that made it work was only used in
   my CLI test; the Edit screen doesn't add it. With an empty box it falls back to `item.prompt`, which for an edited item
   is an *instruction* ("make the net blue"), not a caption. (PROMPT_AUDIT P3.)
2. Style suffixes are keyword lists sent identically to Klein and Qwen (cross-model, tag-style). (P1/P2.)
3. Negative prompts in Wan/LTX graphs are inert at CFG 1 (verified in `comfy/samplers.py:610`; LTX card: "Fixed 8-step
   schedule, CFG=1"). (P6/P7.)
4. Klein exposes a Guidance slider up to 5 on a CFG-1 distilled model. (P12.)
5. Qwen-Image 2.1 runs at 25 steps (template default) vs 40 in the model card, and at ~1.8 MP vs the card's ~4 MP
   buckets (2048², 2752×1536 …). Deliberate for speed; should be a visible "Quality" choice, not silent.
6. `qwen_edit_2511.json` is dead weight (kept by rule).
7. Not under version control.
